# US14 — les mails de régulation

La construction reste dans le style du groupe : fonctions de domaine, ports asynchrones, handlers recevant un objet de dépendances et factories d'adaptateurs.

## Étape 1 : nommer un fait métier

`stationBoundary` décrit une transition vers vide ou pleine. Une lecture ou reconstruction ne déclenche rien. Une station avec un vélo en panne n'est pas physiquement vide. Le domaine ne connaît aucun mail ni agent.

## Étape 2 : enregistrer un mouvement avec son trajet

`BikeMovementRepository` demande un commit commun du mouvement et du trajet. Le double en mémoire et SQLite l'implémentent ; une vérification de version par instantané refuse une station modifiée entre lecture et commit. SQLite conserve l'historique US12, ajoute le vélo et la date de retour par migration additive et termine le trajet sans supprimer son départ.

`TakeBikeHandler` garde son contrat US6 lorsque `movements` n'est pas fourni, pour préserver les tests précédents. Le parcours réel de station fournit ce port ; `ReturnBikeHandler` le reçoit obligatoirement. Les repositories de trajets et de mouvements doivent partager le même stockage. Les nouveaux tests utilisent cette composition explicitement.

## Étape 3 : faire émerger Observer

Une fois le mouvement sauvegardé, les handlers publient `StationEmpty` ou `StationFull` via `EventPublisher`. Ils ne connaissent pas les agents ou les mails. `regulationMail` s'abonne via `EventSubscriptions` et traduit le fait en lettre en réutilisant le port `Mailer` de US8. Le bus en mémoire implémente les deux ports : il notifie chaque auditeur, isole son erreur et la conserve dans `failures`.

C'est le pattern **Observer / publication-abonnement** : une nouvelle réaction s'ajoutera par abonnement, sans modifier la prise ou le retour. Les canaux appli et SMS ne sont pas implémentés dans US14.

Les événements sont transitoires : pas de file persistante ni de reprise automatique. Le bus local conserve les erreurs d'auditeur ; un autre publisher qui échoue ne transforme pas non plus un mouvement déjà enregistré en refus.

## Étape 4 : vérifier les frontières

Le même contrat vérifie mémoire et SQL : départ, retour, écriture directe invalide et lecture périmée. Une panne SQL forcée après l'écriture de station démontre le rollback commun et l'absence de mail. Des parcours SQL réels vérifient aussi les deux notifications, la panne mail et la conservation de l'historique des départs.

Vérifier cette étape avec `node --test "src/**/*.test.ts"`. Les fichiers de test existants des US1 à US13 ne sont pas modifiés.

## Composer les ports

Pour un parcours SQL, `sqlUserRepository`, `sqlOngoingRideRepository` et `sqlBikeMovementRepository` reçoivent la **même** connexion. Injecter `movements` et `events` dans `TakeBikeHandler`, puis les mêmes ports et l'horloge dans `ReturnBikeHandler`. Brancher `regulationMail(events, mailer, adressesDesAgents)` une fois. Les tests SQL donnent cette composition complète.

En mémoire, les factories de trajets et de mouvements reçoivent la même map de trajets ; les dates relues sont copiées. `src/testing/regulationService.ts` fournit un exemple exécutable avec un mailer qui collecte. Un publisher ne doit pas être fourni à un départ sans repository de mouvement : le constructeur refuse cette composition incomplète.
